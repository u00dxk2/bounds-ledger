# Gotchas — bounds-ledger

**Moved out of `CLAUDE.md` on 2026-09-18** because the loaded instruction budget (CLAUDE.md + AGENTS.md) read 61,699 bytes against a ruled 60,000. This is the whole section, byte for byte, extracted by script rather than retyped. `CLAUDE.md` keeps a pointer and the handful of rules that must be loaded before anything runs.

**Read this file before debugging anything in this lane**, and before believing a red, a green, or an absence.


- **NEVER run `doppler configure` or `doppler whoami` in any form — they PRINT the CLI token into the transcript** (fleet rule, effective 2026-08-27, after `doppler configure --json` leaked one into a lane transcript today). This lane does not use Doppler at all and has no reason to invoke it; the line is here so a future agent reaching for a generic secrets-CLI habit stops. Credentials on this machine come from user-scope env at run time (see the global CLAUDE.md § Secrets), and the standing rule that a `catch` block in scope of a secret prints a FIXED STRING applies to any such call. **Blast radius framing, not urgency theatre:** a value in a session transcript is a local + API-log exposure, not a public disclosure, and the right response is a controlled rotation, never an emergency delete that breaks work in flight.
- **NEVER kill a node process by NAME, by AGE, or because it "looks orphaned" — the process table on this machine is shared by all 24 panes** (fleet rule, 2026-08-27). `Get-Process node` lists every lane's listener, waker and worker, not yours. Measured: three lane-side sweeps in one afternoon killed node processes machine-wide, one "reaped 43 orphans" that were other lanes' live listeners. **Only two permitted kill shapes:** (1) a PID you own, read from YOUR pidfile (`tmp/.bus-listen.pid`) or a job record you wrote; (2) a process whose COMMAND LINE contains this lane's repo path — `Get-CimInstance Win32_Process -Filter "name='node.exe'" | Where-Object { $_.CommandLine -match 'bounds-ledger' }` — never a bare `Get-Process node`. Suspect a stray? Post its PID and command line on the bus and LEAVE IT ALONE; the orchestrator holds the census. **Here although we caused none of it, because the failure mode is diagnostic:** we were the VICTIM, and the honest first reading — "my relaunch is broken" — was wrong. Same shape as the rate-limit retraction above.
- **A feature branch gets ZERO CI runs from pushing — `reverify.yml` declares `push: branches: [main]`.** `gh run list --branch <b>` returning an empty list for a pushed branch is the workflow's configuration, not a missing run, and the branch page looks innocuously blank rather than red. `gh workflow run reverify.yml --ref <branch>` is the only route to a runner verdict. Consequence for holds: **a hold whose release condition has no stated command outlives its reason.** The 8/16 primer said "run it on a Linux runner first" and that read as actionable while the obvious action — push and look — could never have produced a run. When you hold work pending a check, write the command, not the check.
- **Check a held branch can still MERGE before spending a runner on it.** On 2026-08-17 a branch was validated on a runner and returned a clean verdict about code that could never land: `main` had moved and both sides had independently fixed the *same lines* differently, so `git merge-tree --write-tree main <branch>` reported a content conflict. **A runner verdict on an unmergeable sha is a verdict about nothing** — the thing that will actually merge is the conflict resolution, which no run has seen. One command, run first.
- **Do not dispatch `reverify.yml` repeatedly** — each run issues ~450 requests (113 individual raw fetches plus ~110 claim URLs), and the scheduled run is the lane's daily alarm. The first run generally already answered the question; validate a conflict resolution locally rather than with a second dispatch. Since b1 (2026-08-17) a PR gets a run automatically, so there is rarely a reason to dispatch at all. **This is practice guidance, not a diagnosis — read the next bullet before repeating the story that used to be attached to it.**
- **A cause you find flattering to admit still needs a positive control.** This bullet once blamed our own dispatch volume for `raw.githubusercontent.com` rate limiting on 2026-08-17; **retracted** — GitHub was in a critical outage 52 minutes before the first dispatch, and three disconfirming facts were in hand and unassembled (a green local ~450-fetch run mid-outage; a later *local* failure although dispatches share no egress with this machine; 502s and 503s, which volume does not produce). The self-blame reached a finding, a commit, an item note and two issue comments unchecked. **Self-blame feels like rigour and is just another unverified attribution — the more dangerous kind, because nobody challenges you for blaming yourself.** The positive-control rule did not fire because the claim was about our own infrastructure. Full account: `A-5 note5`; enforced by `check-self-attribution.mjs`.
- **A FAILED RUN IS NOT A FAILED CHECK — read the JOB layer** (2026-08-26). `check-ci-status`, `gh run list` and the badge all read the run-level `conclusion`, and during a GitHub Actions outage that field was wrong in BOTH directions on this repo inside four minutes: `8a35eaf` reported `completed/failure` with both jobs `queued` and **zero steps executed** (a RED where nothing ran, and no `Drift:` issue because the filing step never ran), while `1cb3f65` reported `startup_failure` over a `check` job that was `completed/success` with **29 of 29 steps**, drift and claims legs included. Read `gh api repos/OWNER/REPO/actions/jobs/<id>` before treating either as a verdict; positive control that the endpoint reports real conclusions is a settled run (`c25cecd` → `completed/success`, 29 and 7 steps). This is the CI-layer twin of the invariant below, and the same discipline: **a check that never ran is UNVERIFIED, not passed and not failed.**
- **`UNREACHABLE` is not `BROKEN`, and the alarm must never title it as one.** `BROKEN` means the read source lost the pin; `UNREACHABLE` means it was never read. A pure HTTP 429 once titled six records as moved because `UNREACHABLE` matched before the `^error:` branch. **The red stays red**—unreachable is unverified—but only true drift gets a `Drift:` title. Finding: `docs/findings/2026-08-17-the-alarm-called-a-rate-limit-a-record-movement.md`.
- **`agent-status`'s `[linter-report]` marker is scoped to the PHYSICAL LINE the WARN quotes, not to the sentence** (measured 2026-08-30, both polarities inside `--validate`: three `sha-file-claim` WARNs fired, one physical line was marked, that one cleared and the other two still fired). A marker placed at the end of a wrapped sentence whose FIRST line was quoted suppresses nothing and silently reads as done. Paste the WARN's quoted fragment, find the physical line it came from, and put the marker there — reflowing the paragraph if needed.
- **`gh api .../issues` counts PULL REQUESTS as issues, and the count lags a close by ~10s.** Both bit on 2026-08-17. The first silently inflated an open-issue count the moment two PRs existed — filter `.pull_request == null`. The second returned "1 open" seconds after closing the last one, three times; two consistent reads settle it. Neither is a bug in the alarm, but both feed a figure this lane reports, and a stale read taken immediately after your own mutation is the shape that looks like a real finding.
- **Closing the issue is part of the drift cycle.** Five resolved drifts sat open as `Drift:` issues for up to six days (#10–#14, closed 2026-08-17 naming their resolving commits). Five standing reds teach the next reader that `Drift:` issues can be ignored, which is the precondition for missing a real one — the founding defect in yet another hat. Close on resolution, naming the sha that resolved it.
- **Prove a dangerous command was neutered BEFORE running an extracted body.** The mirror image of "prove the mutation landed": a throwaway one-liner meant to strip `gh issue create` out of a workflow step before executing it had its escaping silently fail, and it filed a real issue against the public repo. The in-repo harness asserts the strip changed the text (`assert.notEqual(harness, raw)`) and refuses to run otherwise; the debug script did not. Any script that executes a step body verbatim asserts the side effect is gone first.
- **A negative control's restore must not be `git checkout --` while the fix is uncommitted.** Restoring the mutated file that way discarded the uncommitted fix being tested, and `npm test` failing was the only reason it surfaced. Commit or stash, then negative-control.
- **ANY ledger edit invalidates the verify receipt for LEG-ATTRIBUTION, because `check:deferrals` reads `continuity/items.json`** (2026-09-06, three re-runs in one day). The doc-only carve-out in `AGENTS.md` answers *whether a receipt is owed*; it does NOT license reasoning about *which leg is red* from a run that predates the edit — and `continuity/` is doc-shaped, so the carve-out and the blast radius overlap exactly where it is easiest to get wrong. Twice that day the argument "a re-run would change nothing, `check:brief` is permanently red anyway" was made and the receipt gate refused it, correctly: a receipt over changed code cannot say which leg is red NOW, and the re-run is the only thing that can. Both times the inference happened to be right, which is the trap — **a right answer reached by an argument the gate had already refuted teaches the wrong lesson**, and had the `items.json` edit tripped `check:deferrals` the post would have named the wrong red leg with confidence. Re-run at HEAD after touching the ledger; ~450 requests buys the difference between knowing and guessing.
- **A red `--run` stamp from the fleet gate runner may be its shell, not your probe** (2026-09-11). `check-due-gates-dispositioned --run` spawns through cmd.exe on win32, and escaped-quote pairs inside a `node -e "…"` leave a `^` outside cmd's quote state, where it is eaten: `A-42`'s regex reached node as `["]*` and stamped exit 1. Run the stored bytes through bash before believing it. Reported to the orchestrator; it is skylark-site's file, not ours.
- **`check-brief.mjs` exit 3 has THREE causes; you reach for the documented one.** (1) no `CC_PROMPTS_PIN` in env; (2) the 2026-08-02 Supabase wall (`53c87f83`); (3) **2026-09-04 — `/t/*` went Google-session-only and `cc_pin` was retired (S-20260904-25), so `x-cc-pin` signs nobody in.** The brief is fine and now script-unverifiable, so this leg is PERMANENTLY RED — the founding defect. Decision: `A-41`. Never put the PIN in repo secrets. Finding: `docs/findings/2026-08-02-the-brief-check-blamed-the-porter-for-a-login-wall.md`.
- **An HTTP 200 is not evidence you fetched the artifact, and a NEGATIVE result from the wrong document is how you publish a false accusation.** On 2026-08-12 preprints.org returned a 2.6 KB bot page (title `&nbsp;`), while ar5iv returned a real 38 KB arXiv abstract page lacking "Jin" instead of the paper. **Before an absence claim, name a token from the SAME fetch proving the artifact**—here even `numerical range` and `spectral set` were absent. For walled papers, Crossref content negotiation (`api.crossref.org/works/<doi>`) supplies title/author/date, enough for citations and priority claims. Finding: `docs/findings/2026-08-12-two-record-movements-in-one-cycle.md`.
- **erdosproblems.com 403s automated fetch — from DATACENTER IPs, so the block is IP-dependent, and this is why you test a capability from the environment that will EXERCISE it.** Residential Node gets HTTP 200; GitHub Actions gets 403. `C-7` stays `manual: true` / UNVERIFIED in CI while a local `npm run check` genuinely re-verifies it. **A local 200 proves nothing about CI:** automating `C-7` on the strength of one made CI red four minutes later (2026-07-25, `docs/findings/2026-07-25-the-403-that-wasnt.md`). Generalising a laptop result to a runner failed OPTIMISTICALLY — the ledger briefly asserted "zero unverified claims" while the claim gating its north-star watch was silently unverifiable in CI. The only evidence that counts is a green CI run.
- **LF→CRLF git warnings on Windows are benign** — ignore them on commit. **But the files on disk really are CRLF**, which has teeth: a Node/regex string replacement written with `\n` (e.g. `s.replace("- name: X\n        shell: bash\n", …)`) **silently no-ops** — no error, no match, and your "edit" never happened. On 2026-07-25 this produced a false INERT verdict on the pipefail guard during the gate sweep: the guard was fine; the negative control hadn't applied. **Always `git diff` to prove a test mutation landed before believing the result.** Use `\r?\n` in patterns.
- **If a guard or shell refuses a documented command, write it VERBATIM to a file and run that file; never paraphrase inline.** On 2026-08-19 a refused README tamper, `node -e "require('node:fs').appendFileSync(…)"`, was retyped as `require('0node:fs')`; `MODULE_NOT_FOUND` left the mirror untouched, then `reverify.mjs --check` falsely printed `No drift.` at exit 0. This is KP-78's silent half: `git diff --numstat` was empty. Use a quoted heredoc (`cat > /tmp/x.sh <<'EOF'`) containing the exact command. After running it, require a non-empty `git diff --numstat` before reading the detector's verdict; an absent mutation makes either answer meaningless. Retyping tests the retyping, not the documented command—the 2026-08-18 lesson.
- **Never write backslashes through a JS string literal into a file; they can disappear SILENTLY** (2026-08-21: one false claim, dead command, and empty code span). The three non-erroring cases were jq `\(...)` in `releaseTest` printing a literal template; an "unedited" README quote retyped as `-C_{71} > 6.5143...` instead of `-C_{71}\ >\ 6.514326913930565372,`; and `` `\ ` `` becoming an empty span. **Do not retype quoted records—extract them.** Pull the commit line with parsed `git show …`, then require `grep -F -x` hits in source and copy plus a fabricated non-match. Reword decorative backslashes away. The first draft of this bullet itself turned escaped em dashes into mojibake: the SIXTH instance of a fix note reproducing its defect; keep the count because the document is inside this silent-corruption class. **"Verbatim" and "unedited" are method claims**: audit them by grepping the source for the quotation and requiring a hit.
- **Never read an exit code through a pipe — in CI and locally, and this is the lane's founding defect.** GitHub Actions' default runner shell is `bash -e {0}` with no `pipefail`, so `node scripts/reverify.mjs --check | tee ...` reports `tee`'s exit 0 and a real drift passes green: the alarm was fake for this repo's first two days (`docs/findings/2026-07-24-drift-alarm-was-never-armed.md`). CI steps that pipe need `shell: bash`, and `reverify.test.mjs` guards it — do not defeat the guard. The LOCAL form bit again during the 2026-07-25 sweep: `node scripts/check-claims.mjs --selftest | tail -3` reports *`tail`'s* exit 0 while the selftest fails. Redirect to a file and check `$?`, or use `${PIPESTATUS[0]}`.
- **After a `--snapshot`, `git status` over-reports — it is not a content diff.** The snapshot rewrites every mirror file, so files whose *content* is unchanged can still show as modified (line-ending / stat-cache artifact). On 2026-07-28 this showed a third changed file the drift report hadn't named, which looks exactly like "our differ under-reports" — a serious charge in this lane. `git diff --numstat` settled it: zero lines changed, differ was right. **Check `--numstat` before believing `git status` disagrees with the drift report.**
- **The clone count in `npm run traffic` is mostly US and regenerates daily** — 2026-08-20 read 154 cloner-days against 3 viewers, because `reverify.yml` checks out the repo on schedule, on every push and every PR. The sampler deliberately deducts nothing and says so. **The only arrival figure not mostly ours is the viewer count**; a returning-viewer read (`returnRate`, added 2026-09-02) divides viewer-days by GitHub's window-deduplicated head-count and reads REPO views, never page readers.
- **The mirror diff only sees changes *inside* the adopted repo.** Cross-surface divergence (the lane's founding finding) is caught by `check-claims.mjs`, not `reverify.mjs`. Both run in CI.
